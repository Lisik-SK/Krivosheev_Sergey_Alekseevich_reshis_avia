# Решись Авиа · прогноз продаж билетов

Решение блока «Разработка» кейса «Динамическое ценообразование авиабилетов».
Менеджер выбирает направление, дату вылета и цену билета. Приложение сразу показывает,
сколько в самолёте мест, сколько билетов, скорее всего, купят и насколько уверен прогноз.

Реализован самый сложный вариант из условия, **C: веб-страница с backend API**.
Вариант A (скрипт) тоже есть и работает на том же коде расчёта.

## Что реализовано

| Требование из условия | Где и как |
|---|---|
| A. Скрипт «простого прогнозирования» | `npm run forecast -- --from MOW --to AER --date 2026-06-15 --price 9500` ([src/cli/forecast.ts](src/cli/forecast.ts)) |
| B. Веб-форма с расчётом | Форма на странице, логика клиента на TypeScript ([src/client](src/client)) |
| C. Веб-страница + backend API | Страница отправляет данные через `fetch` в `POST /api/forecast`, сервер считает и отвечает JSON ([src/server/routes.ts](src/server/routes.ts)) |
| 1. График распределения спроса при введённой цене | 9 сценариев P10…P90; медиана подписана и совпадает с числом «хотят купить»; число мест отмечено пунктиром; часть спроса, которой не хватит мест, выделена другим цветом. Есть табличный вид и подсказки при наведении мыши и при навигации с клавиатуры |
| 2. Регистрация | Имя, email, пароль; проверка на клиенте и на сервере |
| 3. Авторизация | Вход и выход, сессия в HttpOnly-cookie; прогноз доступен только после входа |
| 4. Размещение на хостинге | Dockerfile, конфиги PM2, systemd и nginx, инструкция в [DEPLOY.md](DEPLOY.md) |

Формула из условия реализована в [src/shared/forecast.ts](src/shared/forecast.ts):

```
хотят = 0.5_base_demand − price_sensitivity × (цена − base_price)
купят = min(seats, max(0, хотят))
```

Для каждого из девяти сценариев берётся свой `X_base_demand`. Дополнительно приложение считает:
- свободные места и загрузку самолёта;
- вероятность того, что желающих будет больше, чем мест (линейная интерполяция между квантилями);
- диапазон, в который спрос попадает с вероятностью 80 % (P10–P90);
- подсказку «цена модели» из колонки `0.5_price` и предупреждение, если цена выходит за пределы `price_min…price_max`.

## Дополнения

| Дополнение | Что даёт | Где |
|---|---|---|
| Кривая выручки и дохода | Видно, при какой цене рейс приносит больше денег. Доход = выручка − `cost_per_passenger` × продажи; максимум найден точно, а не перебором. Клик по графику ставит цену | экран «Рейс», `POST /api/forecast/curve` |
| Календарь загрузки | Загрузка самолёта на каждый день прогноза при выбранной цене, клик открывает день | экран «Рейс», `POST /api/forecast/month` |
| Табло вылетов | Все направления на дату: продажи, места, загрузка, статус; цена базовая или цена модели | экран «Табло», `POST /api/forecast/board` |
| Сравнение двух цен | Цена А и цена Б рядом: продажи, свободные места, загрузка, выручка, доход, риск | переключатель «Сравнить с другой ценой» |
| История и избранное | Расчёты сохраняются в аккаунте, нужные можно закрепить | кнопка «История», `/api/history` |
| Загрузка прогноза через интерфейс | Администратор загружает CSV, видит, что изменится, подтверждает замену или возвращает прошлую версию | экран «Данные», `/api/admin/*` |
| Схема направлений | Дуги из Москвы на карте, толщина — спрос; клик открывает расчёт | экран «Табло» |
| Английская версия | Переключатель RU/EN; на английском и интерфейс, и сообщения сервера | кнопка RU/EN в шапке |

Владелец управляет CSV в разделе «Данные». Чтобы создать его аккаунт, задайте
`INITIAL_ADMIN_EMAIL` и `INITIAL_ADMIN_PASSWORD` перед запуском сервера.
Регистрация через сайт создаёт обычные аккаунты. Подробнее в [инструкции по деплою](DEPLOY.md).

Прогноз продаж и свободные места в интерфейсе округлены до целых билетов. Точные значения (например, 704,5) видны в карточке «Хотят купить», в блоке «Как посчитан прогноз» и в таблице.

## Как заменить прогноз своим (без изменения кода)

Приложение не привязано к конкретным маршрутам, датам и набору квантилей: всё берётся из заголовков и строк CSV.

1. **Заменить файл.** Положите свой файл вместо `data/seasonal_forecast.csv`.
   Сервер сверяет размер и время изменения файлов при запросах, но не чаще чем раз в `DATA_CHECK_INTERVAL_MS`
   (по умолчанию 2 секунды), и перечитывает изменённые файлы без перезапуска.
   При следующем расчёте или при возврате на вкладку в интерфейсе появится уведомление «Загружена новая версия прогноза».
2. **Указать путь.** Задайте переменную окружения
   `FORECAST_PATH=data/Иванов_my_forecast.csv` (и при необходимости `ROUTES_PATH`).
3. **Другая папка.** `DATA_DIR=/srv/forecast`. В этой папке должны лежать `seasonal_forecast.csv` и `routes.csv`.
4. **Через интерфейс.** Администратор открывает экран «Данные» и загружает CSV. Файл сначала проверяется,
   показывается разница с текущими данными, после подтверждения файл заменяется, прошлая версия сохраняется
   как `.bak`, и её можно вернуть одной кнопкой.

Если в новом файле ошибка, сервис продолжит работать на прошлой версии и покажет
жёлтую плашку с причиной: в какой строке и что не так.

Требования к файлу прогноза:
- обязательные колонки `route`, `date`, `seats` и `0.5_base_demand`;
- остальные квантили (`0.1_base_demand` … `0.9_base_demand`), а также `X_price` и `X_price_demand` необязательны, набор может быть любым;
- разделитель: запятая, точка с запятой (экспорт из Excel) или табуляция; дробная часть может отделяться запятой; файл может быть с BOM;
- даты: `2026-06-01`, `2026-06-01 00:00:00` (так пишет pandas), `2026/06/01` или `01.06.2026`;
- если квантили в строке идут не по возрастанию, остальные значения выравниваются по медиане, сама медиана (`0.5_base_demand`) не меняется, а в интерфейсе появляется замечание;
- пустые строки и строки из одних разделителей (`;;;` в конце выгрузки из Excel) пропускаются;
- строки маршрутов, которых нет в `routes.csv`, пропускаются, об этом тоже появляется замечание.

Маршрут из `routes.csv` сразу доступен в списке направлений. Если в файле прогноза ещё нет строк с таким же кодом `route`, калькулятор покажет статус «Прогноз для этого маршрута пока не загружен». Даты и расчёт появятся после загрузки прогноза с совпадающим кодом.

## Быстрый старт

Нужен **Node.js 22.13 или новее** (рекомендуется 24 LTS). Внешняя база данных не нужна:
пользователи хранятся во встроенном SQLite (`node:sqlite`).

```bash
npm ci
npm run build
npm start
```

Откройте http://localhost:3000 и зарегистрируйтесь.
Тестовых аккаунтов в проекте нет: первый пользователь создаётся через форму регистрации.

Режим разработки с автоперезагрузкой: `npm run dev`, затем откройте http://localhost:5173
(Vite проксирует `/api` на сервер, который слушает порт 3000).

### Скрипт (вариант A)

```bash
npm run forecast -- --from Москва --to Сочи --date 15.06.2026 --price 9500 --chart
npm run forecast -- MOW AER 2026-06-15 9500 --json
npm run forecast -- --help
```

После `npm run build` то же самое можно запустить без dev-зависимостей: `node dist/node/cli/forecast.js MOW AER 2026-06-15 9500`.

## API

Все ответы приходят в JSON. Изменяющие запросы (POST, PATCH, DELETE) принимаются только с `Content-Type: application/json` и только со своего домена.
Язык сообщений об ошибках выбирается заголовком `X-Lang: en` (или `Accept-Language`), по умолчанию русский.

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| GET | `/api/health` | все | Состояние сервиса и данных (для мониторинга хостинга) |
| GET | `/api/auth/config` | все | Разрешена ли регистрация |
| GET | `/api/auth/me` | все | Текущий пользователь или `null` |
| POST | `/api/auth/register` | все | `{ name, email, password }` → 201 и cookie сессии |
| POST | `/api/auth/login` | все | `{ email, password }` → cookie сессии |
| POST | `/api/auth/logout` | все | Закрыть сессию |
| GET | `/api/meta` | после входа | Маршруты, даты, диапазоны цен, сведения о файле данных |
| POST | `/api/forecast` | после входа | `{ from, to, date, price }` → прогноз по всем сценариям, выручка и доход |
| POST | `/api/forecast/curve` | после входа | `{ from, to, date }` → выручка и доход при ценах от `price_min` до `price_max`, лучшая цена |
| POST | `/api/forecast/month` | после входа | `{ from, to, price }` → загрузка по всем дням прогноза |
| POST | `/api/forecast/board` | после входа | `{ date?, priceMode: "base" \| "model" }` → все направления на дату |
| GET, POST | `/api/history` | после входа | Список расчётов пользователя / сохранить расчёт `{ from, to, date, price }` |
| PATCH, DELETE | `/api/history/:id` | после входа | Закрепить `{ pinned }` / удалить запись |
| GET | `/api/admin/data` | администратор | Текущие файлы, наличие резервных копий |
| POST | `/api/admin/upload` | администратор | `{ kind: "forecast" \| "routes", filename, content, apply }` → проверка и разница; при `apply: true` замена файла |
| POST | `/api/admin/restore` | администратор | `{ kind }` → вернуть предыдущую версию файла |

Пример запроса прогноза:

```json
POST /api/forecast
{ "from": "MOW", "to": "AER", "date": "2026-06-01", "price": 9500 }
```

В ответе есть `median.wants = 704.5`, `median.sales = 704.5`, `median.freeSeats = 195.5`,
`median.rounded`, массив `scenarios` по всем квантилям и `sellOut`.
Города можно передавать кодом (`MOW`) или названием (`Москва`).

## Тесты

```bash
npm test            # модульные и API-тесты (Vitest)
npm run test:e2e    # браузерные тесты (Playwright), нужен npm run build
npm run test:all    # проверка типов + все тесты + сборка
```

Перед первым запуском браузерных тестов поставьте Chromium: `npx playwright install chromium`.
Браузерные тесты сами поднимают сервер на порту 3399 с чистой базой и копией `data/`. Администратора для тестов
они создают со случайными email и паролем, постоянных тестовых аккаунтов в проекте нет.

Последний прогон: 564 модульных и API-теста (13 файлов) и 192 браузерных теста (по 96 на десктопе и на Pixel 7), все прошли.
Docker-образ собран и проверен: контейнер в статусе `healthy`, процесс работает от пользователя `node`.

Что проверяется:
- формула на всех 155 рейсах при нескольких ценах сверяется с независимым расчётом на Python (`scripts/make_golden.py` → `tests/fixtures/golden.json`);
- свойства формулы на случайных данных (fast-check): продажи всегда в пределах от 0 до числа мест и не растут с ценой;
- разбор CSV: BOM, `;`, дробная часть через запятую, кавычки, ошибки с номером строки;
- API: регистрация, вход, выход, просроченная сессия, CSRF, лимит попыток, заголовки безопасности, горячая замена файла и откат на прошлую версию при ошибке;
- лучшая цена сверяется с полным перебором всех цен для каждого из 155 рейсов;
- дополнения: история, роли, загрузка файла администратором с откатом, табло, календарь, английские сообщения;
- браузер (десктоп и мобильный): весь путь пользователя, график, таблица, сравнение, кривая, календарь, табло, история, загрузка данных, тема, язык, восстановление из URL, доступность (axe).

## Стек

- **Backend:** Node.js 24, TypeScript, Fastify 5, SQLite через встроенный `node:sqlite`. Пароли хешируются через scrypt, от токена сессии в базе хранится только SHA-256.
- **Frontend:** TypeScript без фреймворка, Vite, графики и схема направлений на SVG без библиотек. Цвета графиков проверены на различимость при дальтонизме в обеих темах. Шрифты IBM Plex Sans и IBM Plex Mono лежат в бандле, внешних CDN нет.
- **Общий код:** разбор CSV и формула лежат в `src/shared` и используются сервером и скриптом.
- **Тесты:** Vitest, fast-check, Playwright, axe-core.

Почему так: один язык на клиенте и сервере, нет нативных модулей и внешней БД.
Зависимости ставятся одной командой `npm ci`, приложение работает в Docker или на любом хостинге, где можно запустить сервер на Node.js.

## Безопасность

- Строгая CSP (`script-src 'self'`, без inline-скриптов), `frame-ancestors 'none'`, `nosniff`, HSTS при `COOKIE_SECURE=true`.
- Cookie сессии: `HttpOnly`, `SameSite=Lax`, `Secure` при работе по HTTPS.
- Защита от CSRF: только JSON и проверка `Origin`.
- Лимит попыток входа и регистрации (по умолчанию 10 в минуту с одного IP).
- Одинаковый ответ для неверного пароля и несуществующего email; для несуществующего email проверяется хеш-заглушка, поэтому время ответа почти не отличается.
- Данные из CSV и ответов API выводятся только через `textContent`.
- Экран «Данные» и его API доступны только администратору; файл записывается атомарно (временный файл и переименование), прежняя версия сохраняется.
